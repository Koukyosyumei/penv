# Renode 全ケース互換の実装方針

固定 Renode `c38ac3babcd38a7144b9498e3ca4c2226b76aa37` の公開ランナーで列挙した Robot 304 スイート・2,197インスタンスと NUnit 6プロジェクト・3,413ケースを追跡する。Robot は元のスイートを実行し、NUnit は入力、共通セットアップ、パラメーター、アサーションを保持して Rust に移植する。ホスト除外は上流の条件を根拠に記録する。penv の未対応によるスキップや依存ケースの未実行は残件に含める。

## 共通モニターを先に実装する

通常 CLI、RESC、Robot が同じ Rust のモニターセッションを使う。変数とパス解決、include、マシン選択、プラットフォームの読み込みを先に移す。次いで、仮想時間と UART・ログの待機、状態保存と復帰を本体に実装する。Robot アダプターは RPC と引数・結果の変換を担当する。固定 Renode と同じコマンド列を実行して結果と副作用を比較し、未変更の代表 Robot スイートで確認する。

## 実装順序

| 順序 | 実装単位 | 完了を判断する代表ケース |
|---|---|---|
| 1 | Robot 実行基盤。パス・アセット、スイートとケースの状態、仮想時間、UART とログの観測、エラーの伝達を共通化する。上流で動くケースに対して penv の環境エラーと未対応を区別する。 | STM32F072 と STM32F407 で起動から UART、入力、割り込み、フラッシュのアサーションまで通す。依存ケースは状態を引き継いで実行する。 |
| 2 | CPU・システムバスの共有実装。Cortex-M の例外・バスフォルト・NVIC と RISC-V の CSR・割り込み・トラップを、それぞれ CPU 実装に接続して検証する。 | Cortex-M バスフォルトの例外アサーションと、RISC-V CLIC の144件で終了フックから実際の署名比較まで通す。 |
| 3 | 機種とゲスト環境の縦断対応。CPU、SoC、ボード、ファームウェア、外部接続を一組として扱い、共有するデバイスモデルは共通実装へ入れる。 | 既存の STM32H7・nRF52840 の Zephyr、LiteX・BeagleV の Linux を上流スクリプトで起動し、操作への応答まで確認する。続いて Cortex-R52、OpenTitan、Renesas などを個別に見積もる。 |
| 4 | ホスト連携と動的コード。GDB、外部制御、ネイティブ連携、トレース、Python/C# フックの操作契約を機能ごとに定義する。 | 公式 Renode の代表ケースで操作列と観測結果を確認し、penv の同じ機能を使って元のアサーションを通す。フックは同じゲスト状態で呼び出し、実際の副作用を検証する。 |

順序は依存関係と優先順位を示す。例えば CLIC に必要なフックは第2段階で実装してよい。CLIC 専用の期待値に置き換えず、フック登録、呼び出しと状態参照、終了制御を実装する。C# 動的モデル、GDB、Arm の追加アーキテクチャは代表ケースを最初から最後まで通してから、同じ依存を持つスイート群の工数を見積もる。

NUnit は並行して、既存 API で移せる fixture、DMA やパーサーなど本体 API が必要な fixture、Migrant のように設計と互換性の確認が必要な fixture の順に進める。Migrant は2,247ケースのパラメーター群を調べ、オブジェクトグラフ、参照共有、循環、型やバージョンの扱いなど、実際に上流が検証する契約を確定してから実装単位に分ける。

## 実装と検証のサイクル

1. 全304スイートに主担当と依存機能を付ける。機種・ゲスト環境、CPU・周辺機器、モニター・ホスト連携の依存をケースIDにひも付ける。観測した停止点と、上流スクリプトを読んで見つけた後続の依存は別々に記録する。
2. 共有機能ごとに、その機能を最初に必要とするケース数と、最後のアサーションまで通せる代表ケースを決める。元の Robot と固定 Renode の出力を照合してから実装し、同じ依存を持つスイートをまとめて実行する。
3. 担当別のコミットを統合し、Robot はスイート単位で並列実行する。NUnit は全対象の移植と公式 ID の対応付けを先に揃え、その後に Rust の一括バッチで走らせる。移植途中に動作確認が必要な場合は該当 fixture に限る。ケースIDとパラメーターで前回との差分を取り、退行、アサーション到達、合格、次の停止点を記録する。上流のスキップタグ、依存失敗によるスキップ、ホスト環境不備はそれぞれ理由を残す。
4. 同一の統合コミットで、上流の実行対象が全件合格し、上流が除外するケースの根拠が揃った時点で互換性の完了とする。その後、同じゲスト入力・実行範囲・出力を検証できた負荷で Renode と時間・最大 RSS を比較する。

当面は Robot 担当が CLIC の署名比較を目指し、NUnit 担当が DMA を含む移植を進める。統合とケース台帳は担当間で共有する。日程は、各機能群の代表ケースが最後まで通った時点で、実測の実装工数と残る独立機能の数から見積もる。
