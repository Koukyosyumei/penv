# 共有コードと機種別実装の担当

`penv-arm` が `penv-integration` の統合責任者。バス・マシン・CLI／モニター・REPL／RESC の共通処理、および RV32／RV64 共通の変更を担当する。STM32F072 の未達ケースも、共有作業に余力があるときに進める。

`penv-stm32f407` が `penv-shared-cortexm` で Cortex-M の共通実行系を担当する。命令、例外、MPU、FPU、CPU のリセット、デバッグフック、GDB の Cortex-M 側を扱う。両担当にまたがる変更は、依存するインターフェースを確認し、片方のコミットにまとまるよう調整する。統合ブランチへの取り込みは ARM 担当が行う。

RV32、RV64、STM32H7、nRF52840 の 4 担当は、機種固有のデバイスや命令の実装、上流テスト移植、台帳更新、検証を並列で行う。共有コードにすでに書いた変更は作業履歴に残し、責任者にコミットと再現手順を渡す。以降、共通経路の新しい変更が必要になったら依頼を作る。

## 共有変更の引き渡し

依頼は `~/.local/state/penv-dispatch/shared-requests/<担当>-<一意の短いID>.md` に保存する。一時ファイルに書いてから名前を変更し、対象上流ケース、再現コマンド、期待値と実測、関連コミット、独立して実行できるテストを記録する。配信キューが共通領域に応じて 2 担当のいずれかに優先配信する。依頼側は、引き渡した箇所と独立した仕事を続ける。

担当は依頼ファイルと同名の `.result` にコミット、検証結果、統合状態、または未解決の具体的な条件を書く。Cortex-M 担当は検証済みの共有コミットを `merge-<一意ID>.md` の依頼で ARM 担当に渡し、ARM 担当が統合する。依頼側の作業ツリーでも必要な変更には、取り込み方と再現手順を記録する。関係するブランチでの作業中の差分は保持する。


## 共有変更の処理順

依頼が溜まったら、上流の機能や共通原因で束ね、複数機種の実装を止めるものから処理する。関連する依頼は一つの実装と一回の短い検証で確認し、各依頼にコミットと再現手順を返す。短い検証で確認した範囲と後続の統合回帰の結果を区別する。

Linux 起動などの長い実ファームウェア回帰は、検証対象のコミットから作ったバイナリでバックグラウンド実行する。待つ間は次の共有変更を進める。まとまった統合の区切りで回帰結果を確認し、最終リリースでは対象全件を検証する。
